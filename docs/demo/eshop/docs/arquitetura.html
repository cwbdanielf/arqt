1Introdução e objetivos

Loja virtual de referência onde clientes navegam pelo catálogo, montam o carrinho e fazem pedidos pela web ou pelo celular.

Microsserviços .NET orquestrados pelo Aspire. A loja web (Blazor) e o app móvel consomem APIs de catálogo, carrinho e pedidos; o processamento do pedido (estoque, carência, pagamento) é coreografado por eventos de integração no RabbitMQ, com outbox em PostgreSQL. Identidade centralizada via OpenID Connect.

Capacidades de negócio

  • Catálogo de produtos
  • Carrinho de compras
  • Pedidos
  • Pagamento
  • Identidade e login
  • Webhooks para parceiros
  • Busca semântica e assistente

5Visão de execução

Compra pela loja web Verificado

Do carrinho ao pedido pago, coreografado por eventos.

  1. Cliente → Loja web: Finaliza o checkout
  2. Loja web → Endpoints de pedidos: POST /api/orders
  3. Casos de uso → Outbox de eventos: Grava OrderStarted na transação
  4. Loja web → API de carrinho: Apaga o carrinho
  5. Outbox de eventos → Barramento de eventos: Publica pedido iniciado
  6. Processador de pedidos → Barramento de eventos: Carência encerrada (após GracePeriodTime minutos)
  7. Barramento de eventos → Eventos do catálogo: Valida estoque
  8. Eventos do catálogo → Barramento de eventos: Estoque confirmado
  9. Barramento de eventos → Processador de pagamento: Cobra o pedido
  10. Processador de pagamento → Barramento de eventos: Pagamento aprovado
  11. Barramento de eventos → Loja web: Atualiza status na tela

Notificação a parceiro Verificado

Parceiro recebe aviso quando um pedido é pago.

  1. Parceiro de webhooks → Cliente de webhooks: Cadastra URL de retorno
  2. Cliente de webhooks → API de webhooks: POST /api/webhooks
  3. Barramento de eventos → API de webhooks: Pedido pago
  4. API de webhooks → Cliente de webhooks: POST na URL cadastrada

8Decisões arquiteturais

ADRs inferidos a partir do código — confirme com o time antes de tratá-los como oficiais.

ADR-1 · Orquestração local e deploy com Aspire Verificado

ContextoMuitos serviços e recursos para subir juntos.
DecisãoUm AppHost declara serviços, bancos, fila e referências entre eles.
ConsequênciasSobe tudo com um comando; o deploy fica atrelado ao modelo do Aspire.
Evidênciasrc/eShop.AppHost/AppHost.cs

ADR-2 · Coreografia por eventos com outbox Verificado

ContextoPedido envolve estoque, pagamento e notificação em serviços diferentes.
DecisãoEventos de integração no RabbitMQ, gravados antes num log transacional.
ConsequênciasConsistência eventual; exige monitorar eventos pendentes.
Evidênciasrc/IntegrationEventLogEF

ADR-3 · DDD e CQRS no serviço de pedidos Verificado

ContextoRegras de status do pedido são as mais complexas.
DecisãoDomínio separado (Ordering.Domain), comandos via MediatR e consultas diretas.
ConsequênciasMais camadas, porém regras isoladas e testáveis.
Evidênciasrc/Ordering.Domain, src/Ordering.API/Application

ADR-4 · Carrinho em Redis via gRPC Inferido

ContextoCarrinho muda muito e é por usuário.
DecisãoBasket.API expõe gRPC e grava JSON no Redis.
ConsequênciasRápido, mas sem durabilidade garantida.
Evidênciasrc/Basket.API/Grpc

Chave de assinatura de desenvolvimento Verificado

Impacto: Alto · Probabilidade: Médio · Onde: Identidade

Evidência: Identity.API/Program.cs usa AddDeveloperSigningCredential e desliga KeyManagement (com TODO).

Recomendação: Usar chave gerenciada (Key Vault) antes de produção.

Migração automática na subida Verificado

Impacto: Médio · Probabilidade: Médio · Onde: Identidade

Evidência: AddMigration aplica migrations ao iniciar (comentário diz não recomendado em produção).

Recomendação: Gerar scripts SQL e aplicar no pipeline.

Imagem do Postgres sem versão fixa Verificado

Impacto: Médio · Probabilidade: Médio · Onde: PostgreSQL

Evidência: AppHost usa ankane/pgvector com tag latest.

Recomendação: Fixar a tag da imagem.

Dependências em versão prévia Verificado

Impacto: Médio · Probabilidade: Médio · Onde: API de catálogo

Evidência: EF Core/Npgsql 11 rc e Aspire.Azure.AI.OpenAI preview em Directory.Packages.props.

Recomendação: Atualizar para versões estáveis quando saírem.

Um único Postgres para quatro bancos Verificado

Impacto: Alto · Probabilidade: Baixo · Onde: PostgreSQL

Evidência: catalogdb, identitydb, orderingdb e webhooksdb no mesmo servidor.

Recomendação: Separar ou usar serviço gerenciado com alta disponibilidade.

Carrinho sem persistência Inferido

Impacto: Baixo · Probabilidade: Médio · Onde: Redis

Evidência: Redis sem volume nem persistência declarados no AppHost.

Recomendação: Ativar persistência ou aceitar perda de carrinhos.

11Glossário

AppHostProjeto do Aspire que declara e sobe todos os serviços e recursos.
Evento de integraçãoMensagem publicada no RabbitMQ para avisar outros serviços de uma mudança.
OutboxTabela onde o evento é gravado junto com a transação antes de ser publicado.
Período de carênciaTempo após o pedido em que o cliente ainda pode cancelar antes da validação de estoque.
BFFBack-end for front-end: proxy dedicado ao app móvel.
Busca semânticaBusca por significado usando embeddings guardados no pgvector.
